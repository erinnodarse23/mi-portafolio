## El contexto

Hace unos meses terminé un proyecto de API REST para la gestión de una biblioteca. Lo construí originalmente con **Spring Boot 3.5.16, Java 17 y PostgreSQL 10.5**. Funcionaba bien, pero cuando decidí reestructurarlo para que fuera la carta de presentación de mi portafolio, me propuse un reto: **migrarlo a las últimas versiones LTS disponibles**.

En ese momento, las últimas versiones estables eran:
- **Java 25 LTS** (con Virtual Threads ya consolidados)
- **Spring Boot 4.1.2** (basado en Spring Framework 7)
- **Hibernate 7.4**
- **PostgreSQL 18.6**

En este artículo te cuento qué breaking changes encontré, cómo los resolví y qué resultados obtuve. Porque encontrar documentación actualizada sobre esta migración en español (o incluso en inglés) no es fácil.

## Los breaking changes que encontré

### 1. Jackson 3: el cambio de paquete

El primer error que me lanzó Spring Boot 4 fue por Jackson. La librería cambió de **`com.fasterxml.jackson`** a **`tools.jackson`**. Si tenías imports directos en tu código o configurabas ObjectMapper manualmente, tenías que actualizar todo.

**Solución:** En mi caso no tenía imports directos porque usaba los DTOs con Java Records y dejaba que Spring serializara automáticamente. Pero si usas `@JsonFormat`, `@JsonProperty` u otras anotaciones, debes cambiar los imports.

### 2. Lombok 1.18.44 y Java 23+

Este fue el más frustrante. A partir de **Java 23**, el compilador dejó de procesar las anotaciones de Lombok automáticamente en algunos setups. El error era que el código no reconocía los getters, setters ni constructores generados.

**Solución:** Añadir `annotationProcessorPaths` explícito en el `pom.xml`:

```xml
<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
      <configuration>
        <annotationProcessorPaths>
          <path>
            <groupId>org.projectlombok</groupId>
            <artifactId>lombok</artifactId>
            <version>1.18.44</version>
          </path>
        </annotationProcessorPaths>
      </configuration>
    </plugin>
  </plugins>
</build>
```

Sin esto, el proyecto no compila en Java 25, aunque tengas Lombok en las dependencias.

### 3. Springdoc OpenAPI 3.0.3

La versión anterior de Springdoc (2.x) no era compatible con Spring Boot 4. Tuve que actualizar a **Springdoc 3.0.3**, que genera **OpenAPI 3.1** en lugar de 3.0. La interfaz de Swagger UI es la misma, pero el JSON del spec cambia de formato en algunos detalles.

**Solución:** Actualizar la dependencia en el `pom.xml` y verificar que la URL de Swagger UI sigue siendo `/swagger-ui/index.html`.

### 4. PostgreSQL 18.6 desde PG 10.5

PostgreSQL 10.5 está **EOL (End of Life)** desde noviembre de 2022. Migrar a PostgreSQL 18 supuso varios cambios:

- **`serial` deprecado** en favor de `GENERATED BY DEFAULT AS IDENTITY`
- Cambios menores en la sintaxis de índices
- Mejoras significativas en el planner de queries

**Solución:** Ejecuté los scripts SQL contra un PostgreSQL 18 limpio y ajusté los `CREATE TABLE` para usar las nuevas sintaxis.

## Lo que funcionó sin cambios

Aquí viene la buena noticia: **los 16 tests unitarios pasaron sin modificar una sola línea**.

¿Por qué? Porque los escribí con **Mockito puro, sin `@MockBean`**. Ese detalle marcó la diferencia, porque `@MockBean` fue deprecado en Spring Boot 3.4 y **eliminado en Spring Boot 4** en favor de `@MockitoBean`.

Si tus tests dependen de `@MockBean` o `@SpyBean`, tendrás que refactorizarlos. Yo me libré por haber usado Mockito puro desde el principio.

## Virtual Threads: el gran beneficio

Spring Boot 4 con Java 25 me permitió activar **Virtual Threads** con una sola línea en `application.properties`:

```properties
spring.threads.virtual.enabled=true
```

Con Virtual Threads, Tomcat deja de tener un pool limitado de threads y puede manejar miles de peticiones concurrentes con un consumo de memoria mínimo. Es la evolución natural del modelo "un thread por petición" de toda la vida.

## Resultados medibles

| Métrica | Antes (Spring Boot 3.5 / Java 17) | Después (Spring Boot 4.1 / Java 25) |
|---|---|---|
| **Startup** | ~45 segundos | ~13-17 segundos |
| **Memoria base** | ~350 MB | ~280 MB |
| **Tests unitarios** | 16/16 passing | 16/16 passing (sin cambios) |
| **Versión de OpenAPI** | 3.0 | 3.1 |
| **JDK LTS soportado hasta** | 2026 | 2031 |

El startup pasó de **~45 segundos a ~15 segundos**. Es una mejora de 3x que impacta directamente en el tiempo de despliegue en producción.

## ¿Vale la pena migrar?

**Sí, pero con matices.**

- **Sí migra** si tu proyecto es nuevo o si usas versiones LTS de Java antiguas (11, 17) y quieres aprovechar las mejoras.
- **No migres** si estás en medio de un release crítico o si tu equipo no tiene tiempo para resolver breaking changes.
- **Espera a Spring Boot 4.2** si tu proyecto depende de `@MockBean` en tests, porque la migración de tests a `@MockitoBean` toma tiempo.

Mi caso era ideal porque:
1. El proyecto era mío, sin restricciones de equipo.
2. Ya tenía tests con Mockito puro.
3. Quería aprovechar Virtual Threads para un mejor rendimiento.

## Conclusión

Migrar a las últimas versiones LTS no es solo una cuestión de "estar actualizado". Es una inversión técnica que mejora el rendimiento, la seguridad y la mantenibilidad del proyecto a largo plazo. Los breaking changes son reales, pero manejables si tienes tests automatizados que te avisen cuando algo se rompe.

La lección más importante: **escribe tests con Mockito puro, no con `@MockBean`**. Te ahorrarás una migración dolorosa cuando llegue Spring Boot 4.
